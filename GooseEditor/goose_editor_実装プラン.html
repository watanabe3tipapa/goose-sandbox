01 プロジェクト概要と方針

本画は、Toolsmith Editor と同等の機能を持つローカルファースト Markdown ワークスペースを、新プログラミング言語 Goose で実現することを目的とします。Goose はヒープレス・GC なし・ライフタイム注釈なしのメモリセーフシステム言語であり、C へコンパイル可能なため、ネイティブアプリと WebAssembly の両方を視野に入れた実装が可能です。

基本方針：「コアロジックは Goose で一元実装し、UI は段階的にネイティブ → WebAssembly と拡張する」。これにより、メモリ安全性とパフォーマンスを担保しつつ、最終的にブラウザ上でも動作するエディタを目指します。

02 要件定義

Toolsmith Editor の機能を以下のように分解します。

機能カテゴリ詳細優先度
リッチテキスト編集 段落、見出し、リスト、引用、コードブロックの WYSIWYG 編集 P0
Markdown 双方向変換 編集内容と Markdown ソースのリアルタイム同期 P0
自動保存 ローカルファイルシステムへの差分保存（IndexedDB 相当） P0
エクスポート Markdown / HTML / JSON / Quarto / Plain Text 出力 P1
ワークスペース管理 複数文書のタブ・フォルダ管理 P1
PWA / ブラウザ展開 WebAssembly 化しオフライン動作を実現 P2
テレメトリなし データを外部に送信しないローカルファースト設計 P0

03 ーキテクチャ設計

全体を 3 層に分離し、Goose の強みである「インラインデータ構造」と「安定参照」を最大限に活かします。

3.1 レイヤ構成

// 層構成（Goose モジュール単位）
editor/
  core/
    document.goose    // ドキュメントモデル（ブロックツリー）
    markdown.goose    // Markdown パーサ・シリアライザ
    export.goose      // HTML / JSON / Quarto 変換器
    workspace.goose   // 複数文書・タブ管理
  platform/
    fs.goose          // ファイルシステム抽象（C 標準ライブラリ経由）
    render.goose      // レンダラ抽象インターフェース
  app/
    native_sdl.goose  // SDL2 実装（フェーズ 1）
    wasm_canvas.goose // Emscripten + Canvas（フェーズ 3）
    main.goose        // エントリポイント

3.2 依存方向

  • core は platform に依存しない（純粋ロジック）
  • app は core と platform に依存
  • プラットフォーム差分は extern fn で C ライブラリをラップして吸収

04 フェーズ別実装ロードマップ

PHASE 1 コアエンジン構築 2〜3 週間

core data-model

  • ブロックベースドキュメントモデルの設計（Paragraph, Heading, List, CodeBlock, Quote）
  • CommonMark サブセットパーサの実装（u8[:] スライスでゼロコピー解析）
  • Markdown シリアライザ実装（双方向変換の整合性テスト）
  • Goose の enum.. 可変サイズ列挙型でブロック種別を表現
  • 単体テスト基盤（アサートマクロの整備）
PHASE 2 ネイティブ UI プロトタイプ 3〜4 週間

ui edit

  • SDL2 + software renderer による最小テキストエディタ画面の実装
  • フォントラスタライズ（stb_truetype を extern fn で呼び出し）
  • キャレット移動・選択範囲・入力イベント処理
  • リッチテキストレンダリング（インラインスタイル付きグリフ配置）
  • Markdown ソース表示モードの切り替え UI
PHASE 3 永続化とエクスポート 2 週間

export storage

  • ローカルファイルの読み書き（fopen / fwrite ラッパ）
  • 自動保存タイマー（差分保存ではなく定期フル書き出しで実装簡略化）
  • HTML エクスポート（ブロックツリーを再帰的に走査してタグ生成）
  • JSON エクスポート（ドキュメント構造シリアライズ）
  • Quarto 対応（YAML フロントマターの付加）
PHASE 4 ワークスペース機能 2 週間

workspace model

  • 複数文書のメモリ管理（Document[>..] グローイング配列）
  • タブ切り替え・最近使った文書の追跡
  • フォルダツリー表示（ローカルディレクトリ走査）
  • ワークスペース設定ファイルの読み書き
PHASE 5 WebAssembly 化と PWA 対応 3 週間

wasm pwa

  • Goose → C → Emscripten 経由で WASM ビルド
  • ブラウザ Canvas / WebGL レンダラの実装（フェーズ 2 の抽象を満たす）
  • ブラウザストレージ連携（LocalStorage / OPFS ラッパ）
  • サービスワーカー設定でオフラインキャッシュ
  • レスポンシブレイアウト対応（画面幅に応じたツールバー折り返し）

05 ドキュメントデータモデル

Goose の「インライン可変サイズ構造体」と「スライス」を活用し、ポインタ間接参照を最小化します。

5.1 ブロック定義

// インラインスタイル（可変サイズ列挙型）
enum InlineStyle.. {
    Bold,
    Italic,
    Code,
    Link { url: u8[varint] }
}

// インライン要素：テキスト片＋スタイル配列
struct Inline {
    text: u8[varint],
    styles: InlineStyle..[varint]
}

// ブロック種別（可変サイズ）
enum Block.. {
    Paragraph  { inlines: Inline[varint] },
    Heading    { level: u8, inlines: Inline[varint] },
    ListItem   { bullet: bool, inlines: Inline[varint] },
    CodeBlock  { lang: u8[varint], code: u8[varint] },
    Quote      { blocks: Block..[varint] },
    HorizontalRule
}

// ドキュメント本体：ブロックのグローイング配列
struct Document {
    title: u8[varint],
    blocks: Block..[>..]
}

5.2 設計上の意図

  • Block..[>..]：可変サイズ列挙型のグローイング配列により、1 文書が 1 連続メモリブロックとして保持され、キャッシュ効率が高い
  • InlineStyle..：各スタイルが必要なサイズだけ消費し、メモリ無駄を排除
  • ネスト構造（Quote 内ブロックなど）もインライン展開され、ヒープアロケーションゼロ

06 UI レンダリング戦略

6.1 即時モード GUI アプローチ

Goose はゲームエンジン的な「フレーム毎再描画」に適した言語です。レイアウト計算と描画を毎フレーム実行し、状態保持を最小化します。

// レンダラ抽象（プラットフォーム差分を吸収）
struct Renderer {
    ctx: void&,          // SDL_Renderer* または Canvas コンテキスト
    width: f32,
    height: f32
}

fn render_document(r: Renderer&, doc: Document&, scroll_y: f32) {
    var y = 40.0 - scroll_y;
    for b in doc.blocks {
        match b {
            Paragraph { inlines } => {
                y += render_paragraph(r, inlines, 60.0, y, r.width - 120.0);
            }
            Heading { level, inlines } => {
                y += render_heading(r, level, inlines, 60.0, y);
            }
            // ...
        }
        y += 12.0; // ブロク間マージン
    }
}

6.2 入力イベント処理

  • キー入力は SDL イベントポーリングまたはブラウザ keydown イベントで取得
  • キャレット位置は「ブロックインデックス＋インラインオフセット」の 2 値で表現
  • 選択範囲はアンカーとフォーカスの 2 キャレット位置で保持
  • マウスクリックはレイアウト済み行バッファへのヒットテストで逆変換

07 永続化とエクスポート

7.1 ローカルファイル保存（ネイティブ）

// C 標準ライブラリのラッパ例
extern fn fopen(path: u8[:], mode: u8[:]) -> void&;
extern fn fwrite(buf: void[:], size: u64, n: u64, fp: void&) -> u64;
extern fn fclose(fp: void&);

fn save_document(doc: Document&, path: u8[:]) -> bool {
    var out: u8[>..] = [];
    serialize_markdown(out, doc);
    let fp = fopen(path, "wb");
    if fp == null { return false; }
    fwrite(out[..], 1, out.len, fp);
    fclose(fp);
    return true;
}

7.2 エクスポート形式対応表

形式実装方針備考
Markdown ブロックツリーを CommonMark 構文へ再帰出力 正規形として保持
HTML 各ブロックを対応タグにマッピング インラインスタイルを CSS class に変換
JSON 構造体を JSON オブジェクトとして直列化 ブロック種別を type フィールドで識別
Quarto YAML フロントマター＋Markdown 本体 title / author / date を先頭に挿入
Plain Text すべての装飾を除去してテキストのみ抽出 最も単純な実

08 ビルド・デプロイ計画

8.1 ビルドパイプライン

# ネイティブビルド（開発ループ用）
goose build editor.goose -o goose-editor

# 型チェックのみ（CI 用）
goose check editor.goose

# WASM ビルド（Emscripten 経由）
goose build editor.goose --target=c -o editor.c
emcc editor.c -s WASM=1 -s EXPORTED_FUNCTIONS=... -o editor.js

8.2 デプロイ構成

  • ネイティブ版：Windows / macOS / Linux 向けバイナリを GitHub Releases で配布
  • Web 版：Vercel / GitHub Pages に index.html + editor.wasm + editor.js を配置
  • PWA 化：manifest.json とサービスワーカーでオフラインキャッシュ

09 リスクと対策

リスク影響度対策
Goose の WASM 出力が未成熟 高 フェーズ 5 を後回しにし、まずイティブ版で価値検証
リッチテキスト編集の実装工数 高 最初は Markdown ソース編集モードのみ提供し、WYSIWYG は後追加
日本語入力（IME）対応 中 SDL テキスト入力イベントまたはブラウザ contenteditable 併用を検討
Unicode 正規化・グリフ整形 中 初期版は ASCII + 日本語基本面のみ対応、複雑な文字列処理は C ライブラリ活用
Goose 言語仕様の変更 低 コンパイラバージョンを固定し、追従は月次で計画

10 付録：Goose 言語リファレンス

本計画で頻出する Goose の構文・型をまとめます。

10.1 主要型一覧

型表記意味用途
T[k]固定長配列バッファ固定長
T[]構築時サイズ固定配列不変文字列
T[>..]グローイング配列ブロック一覧、文字列ビルダ
T[:]スライス（ビュー）関数引数、部分文字列
T&参照構造体の受け渡し
T?オプショナル（nullable）存在し得ない値
enum ..可変サイズ列挙型ブロック・スタイル定義

10.2 コマンドライン

goose run editor.goose      // コンパイル＆即時実行（TinyCC バックエンド）
goose check editor.goose    // 型チェックのみ
goose build editor.goose    // 実行ファイル生成
