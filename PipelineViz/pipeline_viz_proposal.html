データ処理工程の「見える化」ダッシュボード

Goose × oh-my-mermaid によるパイプライン可視化ツールの試作提案

2026年10月作成 | 実装: viewer/ | 情報源: Goose 公式・oh-my-mermaid

コンセプトと狙い

データ処理パイプラインは、ステップが増えるほど「何が起きているか」を把握するコストが急増します。本提案は、次の2つのオープンソース技術を接合することで、処理工程そのものを「生きた設計図」として可視化します。

Goose

ヒープなし・GCなし・メモリ安全なシステム言語。JSON/CSVのパース、高速なデータ変換、軽量HTTPエンドポイントの提供に適しています。データスタックによるゼロコピー処理が、メトリクス収集のオーバーヘッドを最小化します。

oh-my-mermaid

コードベースから Mermaid ダイアグラムと7種類のメタ情報を生成・管理するフレームワーク。.omm/ ディレクトリによる「視点（Perspective）」単位の構成と、@class-name によるクラス間リンク機構を持ちます。

組み合わせの核となる発想は、「ダイアグラムを静的なドキュメントではなく、実行時メトリクスを反映するライブ・ビューとして扱う」ことです。Goose が処理パイプラインの内部状態を JSON で出力し、oh-my-mermaid のビューアがそれを読み込んでノードの色やラベルを動的に更新します。

Goose 側の実装設計

Goose の「データスタック・ゼロコピー」特性を活かし、メトリクス収集がパイプライン本体に与える影響をゼロに近づけます。

コアデータ構造

import std;
import json;
import os;

enum Status { Healthy, Warning, Error }

struct StepMetrics {
  step_id: u8[varint],
  records_in: varint,
  records_out: varint,
  elapsed_ms: f64,
  status: Status,
  message: u8[varint],
}

struct PipelineSnapshot {
  timestamp: u8[varint],
  steps: StepMetrics[varint],
}

パイプライン・ラッパー

各ステップを measure() でラップし、実行前後のカウンタ差分を自動記録します。Goose の「スコープ終了時に一括解放」されるデータスタックを利用することで、高頻度処理でもメモリリークのリスクを排除します。

fn measure(step_name: u8[:], input_count: varint,
           f: fn() -> varint) -> StepMetrics {
  let t0 = os.now_ms();
  let out_count = f();
  let elapsed = os.now_ms() - t0;
  return StepMetrics {
    step_id: step_name,
    records_in: input_count,
    records_out: out_count,
    elapsed_ms: elapsed,
    status: Status.Healthy,
    message: "",
  };
}

メトリクス出力（.omm 連携）

パイプライン実行のたびに .omm/data-pipeline/meta.yaml と diagram.mmd を更新します。Goose の JSON サンプル（18_json.goose）と同様、単一のプール内にツリーを構築してから一括書き出しします。

fn emit_snapshot(steps: StepMetrics[:], out_path: u8[:]) {
  var buf: u8[>..] = [];
  json.render(buf, steps);   // 標準ライブラリ json モジュール活用
  os.write_file(out_path, buf);
}

実装ロードマップ

  1. Phase 1 — Goose パイプライン原型
    3ステップのサンプル ETL（Extract → Transform → Load）を Goose で実装し、StepMetrics の計測と JSON 出力を確認します。
  2. Phase 2 — .omm/ 連携
    omm init で data-pipeline / error-handler Perspective を作成し、diagram.mmd に @ リンクを埋め込みます。
  3. Phase 3 — ビューア拡張
    oh-my-mermaid ビューアに live_metrics_url ポーリングを実装し、ノード色・バッジの動的更新を有効化します。
  4. Phase 4 — Diff & Alert
    prev_diagram 比較と、Status.Error 時のサイドバー自動ピン留めを実装します。
  5. Phase 5 — 運用改善
    メトリクス履歴の時系列保存、Goose ワーカースレッドによる並列ステップ計測を検討します。

技術的メリットと留意点

メリット
  • Goose のゼロコピー・データスタックにより、メトリクス収集のメモリオーバーヘッドが極小
  • oh-my-mermaid の Perspective 構造により、パイプラインの「構造」と「状態」を同じ枠組みで管理
  • @step-name リンクで、エラー発生時の原因追跡を直感的に
  • Mermaid テキストベースなので、Git diff でアーキテクチャ変更をコードレビュー可能
留意点
  • Goose に組み込み HTTP サーバーがないため、C FFI または外部サーバー（Python 等）での配信が必要
  • 高頻度更新時は SSE より WebSocket またはポーリング間隔の調整が必要
  • Mermaid の動的 classDef 注入は、大規模ダイアグラムで描画コストが増加する可能性あり
  • oh-my-mermaid 本体へのパッチ方針を事前に検討（fork vs プラグイン）

まとめ

本提案では、Goose の高性能・低オーバーヘッドなデータ処理能力と、oh-my-mermaid の構造化されたアーキテクチャ可視化フレームワークを接合することで、データ処理パイプラインの「構造」と「健康状態」を一枚のダッシュボードに統合する道筋を示しました。

特に、.omm/ ディレクトリを「実行時メトリクスのキャンバス」として再定義し、Mermaid ダイアグラムを静的ドキュメントからライブステータスボードへと昇華させる点が、本試作の独自性となります。

実装済みのプロトタイプは viewer/ で確認できます。サンプルデータとライブシミュレーションにより、提案した UI の挙動をブラウザ上で試せます。
